## Rigidities that stop new knowledge from being represented (inputs to packages 2.1 and 2.2)

1. **Unknown entity class** (`document_extraction.py` l.5092–5094) → `UNRESOLVED`, with no class proposal.
2. **Entity dropped from the package** (`curation.py:attach_scientific_proposals` l.1057–1058): an entity with an unregistered class is skipped (`continue`) and never enters `package["entities"]`.
3. **Statement dropped from the package**: a statement whose class is outside `information_classes` is dropped from `package["statements"]`, and forced to `UNRESOLVED` (l.5691–5693).
4. **Unregistered relation** (l.6254–6256): only a reason code, with no relation proposal (domain, range, qualifiers).
5. **Unresolved endpoints** (l.6407–6415) → `REJECTED` (`UNKNOWN_*_ENDPOINT`). A supported statement or quantity is lost when its subject is missing, where it should be kept as class C evidence.
6. **Closed unit table** (`normalization/units.py`): an unknown unit has no proposal path.
7. **Exact-alias property lookup** (`query/v2.py:resolve_property`): a property with the same name but another unit returns `UNKNOWN`.
8. **Staged property without name–value syntax** (l.3389–3393) → `UNRESOLVED`. Its `property_proposal` is attached to the record but not staged as a candidate.
9. **Composition** (`composition.py:ontology_extension_proposals`): only `hasComponent`, found by fixed English patterns.
10. **Concept proposals** (`curation.py:propose_concept`) require already-approved parents and relations, a fixed direction, and no transitive or inverse relations. Extraction never calls it.

These rigidities line up with package 1.2: class B rejections (contract too rigid) and class C ones (association incomplete, where an endpoint is rejected instead of kept).
